Mental modelWhat replaces the DOM?

The accessibility tree is the desktop DOM

Desktop applications expose a semantic hierarchy to assistive technology and automation clients. Names differ by platform, but the useful fields are similar.

Windows

UI Automation (UIA)

Desktop root -> app window -> toolbar -> button -> list item. Controls expose properties and action patterns.

macOS

Accessibility API (AX)

Applications expose accessible elements, roles, attributes, actions, children, and bounds.

Linux

AT-SPI

Desktop applications publish accessible objects and actions through the accessibility bus.

Lane 1Perfect the CLI-first path

Turn common computer work into typed commands

Opening and closing apps is valid CLI work, but it is only the lifecycle layer. Real coverage comes from combining lifecycle control with app capabilities and verification.

1. Lifecycle

Open, focus, list, status, quit, restart. Implement once behind a cross-platform appctl adapter.

2. Capability

Use native CLIs, APIs, document formats, scripting bridges, plugins, or generated CLI-Anything harnesses.

3. Evidence

Read process state, exit code, JSON output, changed files, app state, or an accessibility-tree event.

Cross-platform lifecycle examples

OSOpenQuitObserve
macOSopen -a "App"osascript ... quitpgrep -fl App
Linuxgtk-launch APP_IDpkill -TERM namepgrep -af name
WindowsStart-Process appStop-Process -Name appGet-Process app

Wrap operating-system commands behind one schema. Do not let the model invent raw shell text.

CLI-Anything's role

Use it to create or adopt a stateful command-line harness for software whose useful functions are otherwise trapped behind a graphical interface.

A harness should offer discoverable commands, structured JSON output, undo where possible, and tests against the real application.

What it does not solve

Launching a process is not the same as controlling its document, scene, timeline, or settings. Some apps expose no clean backend, and generated wrappers still require maintenance and verification.

appctl open obs appctl status obs --json appctl focus obs cli-anything-obs --json scene switch --name "Camera" appctl verify obs --expect-window "OBS Studio"
Target: take the workflows that are eligible for structured control and drive that class toward 100% coverage. The "40%" is a hypothesis until your own benchmark proves it.
Commands are the control plane, not just the launcher4
Lane 3Keyboard as a workflow node

Vim is not the problem. Blindness is.

A keyboard sequence becomes agent-grade when it has a contract. Treat it like an n8n node: typed inputs, declared preconditions, bounded execution, observable outputs, and a recovery path.

Keyboard node = macro + focus + state + timeout + proof

Strong keyboard pipeline

  • Named intent: editor.save_all
  • Precondition: editor is foreground; no modal dialog
  • Input: file path or buffer selector
  • Sequence: validated keys, not free-form text
  • Postcondition: dirty flag cleared or file timestamp changed
  • Recovery: Escape, refocus, retry once, then escalate

Weak keyboard pipeline

  • Assumes the correct window has focus
  • Uses a fixed number of Tab presses
  • Sleeps for arbitrary durations
  • Cannot detect a popup or changed layout
  • Repeats destructive keys after uncertainty
  • Reports success because keys were sent

Node contract

{
  "id": "vim.apply_refactor",
  "inputs": {"file": "string", "macro": "approved_id"},
  "requires": ["vim_mode=normal", "buffer_loaded"],
  "action": {"keys": ["@r"]},
  "expect": ["buffer_changed", "diagnostics_not_increased"],
  "timeout_ms": 3000,
  "on_fail": ["escape", "capture_state", "escalate"]
}

Where keyboard nodes shine

Editors

Vim motions, command palettes, save/build/test loops, repeatable refactors.

Terminal multiplexers

Create panes, route commands, capture pane output, attach to named sessions.

Stable applications

Known shortcuts for new/open/export, provided state can be checked before and after.

Design rule: use keys as an actuator, not as perception. Read focus and state from the accessibility tree, process table, editor API, filesystem, or captured terminal output.

Make the small model choose, not hallucinate

A tiny local language model can route intent, fill arguments, rank elements, and select recovery steps. It should not generate unconstrained shell commands or invent coordinates.

Model profile to benchmark

  • 0.5B to 0.8B parameters
  • 4-bit quantization where quality holds
  • Grammar-constrained JSON output
  • Short context built from retrieved tool specs
  • Fast enough to run on every action

Under 1 GB should be treated as a disk/RAM budget to verify on the actual runtime, not a quality guarantee.

Keep outside the model

  • Permissions and destructive-action gates
  • Shell quoting and process management
  • Path normalization and file checks
  • Retries, timeouts, and idempotency
  • Evidence collection and audit logs
Browser savings: route browser tasks through API or DOM extraction first. Let the local model map intent to a known action. Use local OCR or a local vision model only when the page hides semantics, and reserve paid remote vision for unsupported edge cases.

System designDiscrete computer-use pipeline

One loop, five lanes, explicit escalation

The planner emits one typed action at a time. Every action must name an expected state change. Failure moves down one lane; it never triggers an unbounded retry loop.

StageResponsibilityOutput
1. ObserveCollect process list, active window, DOM/a11y tree, screenshot, terminal outputRaw state bundle
2. NormalizeReduce to app, role, name, value, state, bounds, confidenceCompact state
3. RouteChoose API/CLI, semantic tree, keyboard node, local vision, or raw inputLane + tool candidates
4. PlanSelect one action and define its expected effectTyped action
5. ValidateCheck schema, allowlist, arguments, permissions, and riskApproved or blocked
6. ActRun exactly one adapter, node, or actuatorExecution result
7. VerifyRe-observe and compare actual state with expected stateEvidence verdict
8. RecoverRetry safely, switch lane, restore state, or ask a humanNext action
9. LearnRecord trace, failure cause, and reusable workflow candidateBenchmark data

Implementation planFrom hypothesis to measured coverage

Perfect a bounded workflow set before chasing universality

Phase 1: inventory

  • Log 50 real computer tasks
  • Split each into atomic actions
  • Mark current best lane
  • Count frequency and failure cost

Phase 2: adapters

  • Build cross-platform appctl
  • Register existing CLIs and APIs
  • Add CLI-Anything harnesses selectively
  • Require JSON and evidence hooks

Phase 3: keyboard nodes

  • Package Vim/tmux/editor macros
  • Declare focus preconditions
  • Add postcondition checks
  • Test interruption and recovery

Phase 4: semantic + vision

  • Add OS accessibility adapters
  • Use local OCR before vision
  • Benchmark a sub-1GB router
  • Add local visual grounding fallback

Quick referenceRemember this page

The five-second routing test

  1. Can a command or API do it? Use that. Wrap it behind a typed tool.
  2. Can the DOM or accessibility tree name it? Select the semantic element and invoke its action.
  3. Is there a stable keyboard workflow? Call a verified macro node with focus and postconditions.
  4. Are semantics missing? Use local OCR and local visual grounding.
  5. Only coordinates remain? Click once, re-observe immediately, and stop on mismatch.

Core vocabulary

Observer: collects machine and UI state.

Normalizer: turns platform-specific state into one schema.

Router: chooses the cheapest reliable lane.

Grounder: maps an intended target to an element or location.

Actuator: sends a command, action, key, or pointer event.

Verifier: proves that the intended state changed.

Architecture in one line

goal -> state -> route -> typed action -> guard -> execute -> evidence -> recover

What to build first

  1. appctl for open/focus/status/quit
  2. Tool registry with JSON schemas
  3. Vim/tmux macro-node runner
  4. Windows/macOS/Linux a11y adapters
